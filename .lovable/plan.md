

# Eliminate Shared Secret: DB-Side HMAC Token Authentication for Cron

## Problem

On Lovable Cloud, there is **no secure path** to inject a secret into the database (Vault, GUC settings, or otherwise) without it appearing in SQL text -- which defeats the purpose of rotation. The `secrets` tool only covers Edge Function env vars.

Meanwhile, two cron jobs still have the old compromised secret hardcoded in `cron.job.command`.

## Solution: Self-Authenticating HMAC Tokens (No Shared Secret)

Instead of a static shared secret between the database and Edge Functions, generate a signing key **entirely within the database** using `gen_random_bytes(32)`. The key value never appears in any SQL statement, migration, or log. Cron sends a short-lived HMAC token; the Edge Function verifies it by calling back to the database.

```text
pg_cron
  |
  v
get_cron_headers()  -->  HMAC(timestamp, internal_key) --> token
  |
  v
net.http_post(headers: {X-Cron-Timestamp, X-Cron-Token})
  |
  v
Edge Function receives headers
  |
  v
supabase.rpc('verify_cron_token', {timestamp, token})
  |
  v
verify_cron_token()  -->  recompute HMAC, compare, check +-120s window
  |
  v
Authorized (or 401)
```

## Security Properties

- Signing key generated server-side by `gen_random_bytes(32)` -- **never appears in SQL text, logs, or migration files**
- Key stored in a table with RLS enabled and **zero policies** (inaccessible via PostgREST/API)
- Only `SECURITY DEFINER` functions can read the key
- Tokens are time-limited (120-second replay window)
- No Vault needed
- `CRON_SECRET` Edge Function env var can be removed after migration
- `cron.job.command` contains no secrets at all

## Implementation Steps

### Step 1: Migration -- Create key table, generate key, update functions

A single migration that:

1. Creates `internal_keys` table with RLS enabled, no policies:
```sql
CREATE TABLE IF NOT EXISTS public.internal_keys (
  name text PRIMARY KEY,
  key_value bytea NOT NULL DEFAULT extensions.gen_random_bytes(32),
  created_at timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE public.internal_keys ENABLE ROW LEVEL SECURITY;
-- No RLS policies = no access via PostgREST API
```

2. Inserts the signing key (value generated by `gen_random_bytes`, never in SQL):
```sql
INSERT INTO public.internal_keys (name)
VALUES ('cron_auth')
ON CONFLICT DO NOTHING;
```

3. Replaces `get_cron_headers()` to generate HMAC tokens:
```sql
CREATE OR REPLACE FUNCTION public.get_cron_headers()
RETURNS jsonb
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = 'public'
AS $$
DECLARE
  ts text;
  signing_key bytea;
  token text;
BEGIN
  ts := extract(epoch from now())::bigint::text;
  SELECT key_value INTO signing_key
    FROM internal_keys WHERE name = 'cron_auth';
  token := encode(
    extensions.hmac(ts::bytea, signing_key, 'sha256'),
    'hex'
  );
  RETURN jsonb_build_object(
    'Content-Type', 'application/json',
    'X-Cron-Timestamp', ts,
    'X-Cron-Token', token
  );
END;
$$;
```

4. Creates `verify_cron_token()` for Edge Functions to call:
```sql
CREATE OR REPLACE FUNCTION public.verify_cron_token(
  p_timestamp text, p_token text
)
RETURNS boolean
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = 'public'
AS $$
DECLARE
  signing_key bytea;
  expected text;
BEGIN
  IF abs(extract(epoch from now()) -
         p_timestamp::bigint) > 120 THEN
    RETURN false;
  END IF;
  SELECT key_value INTO signing_key
    FROM internal_keys WHERE name = 'cron_auth';
  IF signing_key IS NULL THEN RETURN false; END IF;
  expected := encode(
    extensions.hmac(p_timestamp::bytea, signing_key, 'sha256'),
    'hex'
  );
  RETURN expected = p_token;
END;
$$;
```

### Step 2: Update all 3 Edge Functions

Replace the `X-CRON-SECRET` header check with HMAC token verification via RPC.

**Before** (in each function):
```typescript
const cronSecret = Deno.env.get("CRON_SECRET");
const reqSecret = req.headers.get("X-CRON-SECRET");
if (!cronSecret || !reqSecret || reqSecret !== cronSecret) {
  return unauthorized();
}
```

**After**:
```typescript
const timestamp = req.headers.get("X-Cron-Timestamp");
const token = req.headers.get("X-Cron-Token");
if (!timestamp || !token) {
  return unauthorized();
}
const { data: isValid } = await supabase.rpc("verify_cron_token", {
  p_timestamp: timestamp,
  p_token: token,
});
if (!isValid) {
  return unauthorized();
}
```

Files changed:
- `supabase/functions/process-scheduled-actions/index.ts`
- `supabase/functions/process-policy-rules/index.ts`
- `supabase/functions/cleanup-maintenance/index.ts`
- `supabase/functions/execute-action-server/index.ts` (the `authenticate()` function's cron path)

CORS headers updated: replace `x-cron-secret` with `x-cron-timestamp, x-cron-token` in `Access-Control-Allow-Headers`.

### Step 3: Reschedule cron jobs (change-data SQL, no secrets)

Unschedule all three jobs and recreate using the updated `get_cron_headers()`:

```sql
SELECT cron.unschedule('process-scheduled-actions');
SELECT cron.unschedule('process-policy-rules');
SELECT cron.unschedule('cleanup-maintenance-5min');

SELECT cron.schedule(
  'process-scheduled-actions', '* * * * *',
  $$ SELECT net.http_post(
    url := '...functions/v1/process-scheduled-actions',
    headers := public.get_cron_headers(),
    body := '{"source":"cron"}'::jsonb
  ) AS request_id; $$
);
-- (same pattern for other two jobs)
```

### Step 4: Verify and clean up

1. Query `SELECT command FROM cron.job` -- confirm no secrets in any command
2. Call `SELECT public.get_cron_headers()` -- confirm it returns HMAC-based headers
3. Wait one cron cycle, check Edge Function logs for HTTP 200
4. Optionally remove `CRON_SECRET` from Edge Function env vars (no longer needed)

## What This Eliminates

- No static shared secret anywhere (no CRON_SECRET env var needed)
- No secret in Vault, SQL text, migration files, or cron.job.command
- No manual steps (everything is automatable via migration + code changes)
- Signing key is fully server-generated and server-contained
